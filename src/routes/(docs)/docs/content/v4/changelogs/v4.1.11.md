Release date: **October 27, 2026**

> [!IMPORTANT]
> This release fixes a security issue in v4.0.0 to v4.1.10. Upgrade, then check whether you need to rotate the secrets stored in your monitors and triggers. See [Security](#security).

## Security {#security}

### Monitor and trigger secrets were readable with read-only access {#monitor-secrets}

| Field             | Value                                                                       |
| ----------------- | --------------------------------------------------------------------------- |
| Affected versions | v4.0.0 to v4.1.10                                                           |
| Fixed in          | v4.1.11                                                                     |
| Severity          | Medium, CVSS 3.1 score 6.5 (`CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N`) |
| Weakness          | CWE-522 (Insufficiently Protected Credentials)                              |

These read paths returned stored secrets in plain text:

- The REST API returned the full `type_data` of each monitor from `GET /api/v4/monitors`, `GET /api/v4/monitors/{tag}`, and the response of `PATCH /api/v4/monitors/{tag}`, to any valid API key.
- The dashboard API (`POST /manage/api`) returned the full `type_data` of each monitor from the `getMonitors` action. This action needs only `monitors.read`.
- The dashboard API returned each trigger's URL and headers from the `getTriggers` action, which needs only `triggers.read`, and from the alert configuration actions, which need only `alerts.read`.

All three built-in roles have these read permissions, including **Member**. These values were readable:

- Each `headers` value of an API or Prometheus monitor, such as `Authorization: Bearer ...`.
- The request `body` of an API monitor.
- The `proxy` URL, with its user name and password.
- The `connectionString` of a SQL monitor.
- The `secretString` of a heartbeat monitor. A user who knows it can send fake heartbeats.
- The `tlsKey` of a Docker monitor.
- The URL and each header value of a webhook, Slack, or Discord trigger. A Slack or Discord webhook URL lets anyone post to that channel.

Kener now shows each monitor value as `********` in the REST API, except in the `POST /api/v4/monitors` response, and in the dashboard. The dashboard shows a trigger URL as its origin plus `/********`, and each trigger header value as `********`. Users with `monitors.write` still see the heartbeat secret in the dashboard, so they can copy the heartbeat URL. Monitor checks and alerts still use the real values. See [Stored secrets](/docs/v4/monitors/overview#stored-secrets).

What to do:

1. Upgrade to v4.1.11.
2. If anyone held an API key, or had a role with a read permission above, and you did not trust them with these values, treat the values as exposed. Rotate each one where it was issued: the API token, the database password, the proxy password, the Docker TLS key, or the webhook URL.
3. For each heartbeat monitor, set a new **Heartbeat secret** in the monitor settings, or click **New URL**. Then give the new URL to the sender.

A value written as a `$SECRET` reference, such as `Bearer $API_TOKEN`, stays in an environment variable. Kener returned only the reference, so that secret was not exposed.

> [!NOTE]
> A save that sends a masked value back keeps the stored secret, in the dashboard and in `PATCH /api/v4/monitors/{tag}`. To change a secret, send the new value.
