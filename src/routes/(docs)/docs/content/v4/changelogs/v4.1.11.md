Release date: **November 2, 2026**

> [!IMPORTANT]
> This release fixes a security issue in v4.0.0 to v4.1.10. Upgrade, then check whether you need to rotate the secrets stored in your monitors and triggers. See [Security](#security).
>
> `/api/v4` writes now return `400` for a request body that the API spec forbids. Before, some of these requests returned `500`, and some stored a changed value. See [API changes](#api-changes).

## Security {#security}

### Monitor and trigger secrets were readable with read-only access {#monitor-secrets}

| Field             | Value                                                                       |
| ----------------- | --------------------------------------------------------------------------- |
| Affected versions | v4.0.0 to v4.1.10                                                           |
| Fixed in          | v4.1.11                                                                     |
| Severity          | Medium, CVSS 3.1 score 6.5 (`CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N`) |
| Weakness          | CWE-522 (Insufficiently Protected Credentials)                              |

These read paths returned stored secrets in plain text:

- The REST API returned the full `type_data` of each monitor from `GET /api/v4/monitors`, `GET /api/v4/monitors/{tag}`, and the response of `PATCH /api/v4/monitors/{tag}`, to any valid API key.
- The dashboard API (`POST /manage/api`) returned the full `type_data` of each monitor from the `getMonitors` action. This action needs only `monitors.read`.
- The dashboard API returned each trigger's URL and headers from the `getTriggers` action, which needs only `triggers.read`, and from the alert configuration actions, which need only `alerts.read`.

All three built-in roles have these read permissions, including **Member**. These values were readable:

- Each `headers` value of an API or Prometheus monitor, such as `Authorization: Bearer ...`.
- The request `body` of an API monitor.
- The `proxy` URL, with its user name and password.
- The `connectionString` of a SQL monitor.
- The `secretString` of a heartbeat monitor. A user who knows it can send fake heartbeats.
- The `tlsKey` of a Docker monitor.
- The URL and each header value of a webhook, Slack, or Discord trigger. A Slack or Discord webhook URL lets anyone post to that channel.

Kener now shows each monitor value as `********` in the REST API, except in the `POST /api/v4/monitors` response, and in the dashboard. The dashboard shows a trigger URL as its origin plus `/********`, and each trigger header value as `********`. Users with `monitors.write` still see the heartbeat secret in the dashboard, so they can copy the heartbeat URL. Monitor checks and alerts still use the real values. See [Stored secrets](/docs/v4/monitors/overview#stored-secrets).

What to do:

1. Upgrade to v4.1.11.
2. If anyone held an API key, or had a role with a read permission above, and you did not trust them with these values, treat the values as exposed. Rotate each one where it was issued: the API token, the database password, the proxy password, the Docker TLS key, or the webhook URL.
3. For each heartbeat monitor, set a new **Heartbeat secret** in the monitor settings, or click **New URL**. Then give the new URL to the sender.

A value written as a `$SECRET` reference, such as `Bearer $API_TOKEN`, stays in an environment variable. Kener returned only the reference, so that secret was not exposed.

> [!NOTE]
> A save that sends a masked value back keeps the stored secret, in the dashboard and in `PATCH /api/v4/monitors/{tag}`. To change a secret, send the new value.

## API changes {#api-changes}

Each `/api/v4` write now checks its JSON body against the [API spec](/docs/spec/v4/) before it saves anything. A body that the spec forbids returns `400` with code `BAD_REQUEST`, and the message names the field, for example `description must be a string or null`. Before, a list in `description` returned `500`, and the number `123` was stored as the text `123.0` ([#912](https://github.com/rajnandan1/kener/issues/912)).

These requests now return `400`:

- A body that is not a JSON object, such as `null` or `[]`. Before, 14 of the 15 writes returned `500` for `null`.
- A number, boolean, list, or object in a text field, for example `"description": 123`.
- A string where the spec asks for a number, for example `"confirmation_threshold": "5"`, and a decimal where it asks for an integer, for example `"start_ts": 1.5`.
- On `POST /api/v4/monitors` and `PATCH /api/v4/monitors/{tag}`, a value that is not in the allowed list: `status` takes `ACTIVE` or `INACTIVE`, and `default_status` takes `UP`, `DOWN`, `DEGRADED`, or `MAINTENANCE`. `is_hidden` and `include_degraded_in_downtime` take `YES` or `NO`. `monitor_type` takes one of the 13 monitor types.
- `null` in a field that cannot be empty, for example `status` or `monitor_type` on a monitor, or the `timestamp` of an incident comment.

These requests still work:

- `null` clears a text field: `description`, `image`, `cron`, `category_name`, and `external_url` on a monitor, `page_subheader` and `page_logo` on a page, and `description` on a maintenance. `null` in `end_date_time` still reopens an incident.
- A field that the spec does not list is ignored, so you can send back a body that you read with `GET`.

`PATCH /api/v4/monitors/{tag}` now saves `include_degraded_in_downtime`. Before, it ignored the field and kept the stored value.

Some error messages changed. For example, a request with no `title` now returns `title is required`.

## Dependencies {#dependencies}

This release updates dependencies with `npm audit fix`, within the version ranges in `package.json`. `npm audit --omit=dev` now reports 10 known vulnerabilities instead of 39, and 2 high-severity ones instead of 26. The updated packages include axios, undici, dompurify, devalue, lodash, js-yaml, nanoid, mysql2, `@grpc/grpc-js`, form-data, postcss, vite, and `@sveltejs/kit` ([#911](https://github.com/rajnandan1/kener/pull/911)). The two high-severity ones left, nodemailer and sharp, need a new major version.

## Docker image tags {#docker-image-tags}

The comment in `docker-compose.yml` and the Alpine image-size badge in the README pointed at `rajnandan1/kener:alpine`. That tag stopped updating in August 2025 and still serves v3. Both now point at `rajnandan1/kener:latest-alpine`, which each release updates ([#914](https://github.com/rajnandan1/kener/pull/914)).

> [!WARNING]
> If you run `rajnandan1/kener:alpine`, you run v3. Switch to `rajnandan1/kener:latest-alpine`, or pin a version such as `rajnandan1/kener:v4.1.11-alpine`.
