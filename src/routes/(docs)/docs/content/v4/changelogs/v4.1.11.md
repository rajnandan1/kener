Release date: **October 27, 2026**

> [!IMPORTANT]
> This release fixes three security issues in v4.0.0 to v4.1.10. Before you upgrade, rename each environment variable that a monitor or trigger references, for example `API_TOKEN` to `KENER_VAR_API_TOKEN`. See [Environment variables](#env-variables). After you upgrade, check whether you need to rotate secrets. See [Security](#security).

## Security {#security}

### Monitor and trigger secrets were readable with read-only access {#monitor-secrets}

| Field             | Value                                                                       |
| ----------------- | --------------------------------------------------------------------------- |
| Affected versions | v4.0.0 to v4.1.10                                                           |
| Fixed in          | v4.1.11                                                                     |
| Severity          | Medium, CVSS 3.1 score 6.5 (`CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N`) |
| Weakness          | CWE-522 (Insufficiently Protected Credentials)                              |

These read paths returned stored secrets in plain text:

- The REST API returned the full `type_data` of each monitor from `GET /api/v4/monitors`, `GET /api/v4/monitors/{tag}`, and the response of `PATCH /api/v4/monitors/{tag}`, to any valid API key.
- The dashboard API (`POST /manage/api`) returned the full `type_data` of each monitor from the `getMonitors` action. This action needs only `monitors.read`.
- The dashboard API returned each trigger's URL and headers from the `getTriggers` action, which needs only `triggers.read`, and from the alert configuration actions, which need only `alerts.read`.

All three built-in roles have these read permissions, including **Member**. These values were readable:

- Each `headers` value of an API or Prometheus monitor, such as `Authorization: Bearer ...`.
- The request `body` of an API monitor.
- The `proxy` URL, with its user name and password.
- The `connectionString` of a SQL monitor.
- The `secretString` of a heartbeat monitor. A user who knows it can send fake heartbeats.
- The `tlsKey` of a Docker monitor.
- The URL and each header value of a webhook, Slack, or Discord trigger. A Slack or Discord webhook URL lets anyone post to that channel.

Kener now shows each monitor value as `********` in the REST API, except in the `POST /api/v4/monitors` response, and in the dashboard. The dashboard shows a trigger URL as its origin plus `/********`, and each trigger header value as `********`. Users with `monitors.write` still see the heartbeat secret in the dashboard, so they can copy the heartbeat URL. Monitor checks and alerts still use the real values. See [Stored secrets](/docs/v4/monitors/overview#stored-secrets).

What to do:

1. Upgrade to v4.1.11.
2. If anyone held an API key, or had a role with a read permission above, and you did not trust them with these values, treat the values as exposed. Rotate each one where it was issued: the API token, the database password, the proxy password, the Docker TLS key, or the webhook URL.
3. For each heartbeat monitor, set a new **Heartbeat secret** in the monitor settings, or click **New URL**. Then give the new URL to the sender.

A value written as a `$SECRET` reference, such as `Bearer $API_TOKEN`, stays in an environment variable. Kener returned only the reference, so that secret was not exposed.

> [!NOTE]
> A save that sends a masked value back keeps the stored secret, in the dashboard and in `PATCH /api/v4/monitors/{tag}`. To change a secret, send the new value.

### Monitor URL secrets were readable, and a changed destination received stored secrets {#secret-destination}

| Field             | Value                                          |
| ----------------- | ---------------------------------------------- |
| Affected versions | v4.0.0 to v4.1.10                              |
| Fixed in          | v4.1.11                                        |
| Weakness          | CWE-522 (Insufficiently Protected Credentials) |

Two gaps stayed open next to the [fix above](#monitor-secrets):

- **A token in a monitor URL was readable.** The REST API and the dashboard `getMonitors` action returned the `url` of an API or Prometheus monitor as stored, for example `https://api.example.com/health?token=abc123` or `https://user:pass@host/health`. Any API key and the built-in **Member** role could read it.
- **A changed destination received the stored secrets.** A caller with write access could change a monitor `url` and send `********` back, or leave the headers out of a `PATCH /api/v4/monitors/{tag}`. The next check sent the stored header values, body, and proxy credentials, with `$SECRET` references resolved, to the new URL. The same worked for a trigger URL, for the Docker `daemon` in the container picker, and for the OIDC `issuer_url`, which received the stored `client_secret` at the next sign-in. Any API key and the built-in **Editor** role could do this.

Kener now shows a monitor `url` and `proxy` as their origin only, for example `https://api.example.com/********`. Kener restores a masked secret only while every destination of the record stays as saved: the monitor `url`, `proxy`, Docker `daemon` and `connectionType`, the trigger URL, and the OIDC `issuer_url`. A save that changes a destination must send each secret again. Otherwise it fails with `400` and names the fields to send. See [Stored secrets](/docs/v4/monitors/overview#stored-secrets).

What to do:

1. Upgrade to v4.1.11.
2. If anyone held an API key or the `monitors.read` permission while a monitor URL carried a token, rotate that token.
3. If anyone held an API key or a `.write` permission for monitors, triggers, or settings, and you did not trust them with your stored secrets, rotate the secrets as the [fix above](#monitor-secrets) describes, and the OIDC client secret.
4. Move each token in a monitor URL into a `$SECRET` reference, for example `https://api.example.com/health?token=$HEALTH_TOKEN`.

> [!NOTE]
> To change a monitor URL in the dashboard, type the full URL, then enter its header values, body, and proxy again.

### A monitor or trigger could send any environment variable to its destination {#env-variables}

| Field             | Value                                                                |
| ----------------- | -------------------------------------------------------------------- |
| Affected versions | v4.0.0 to v4.1.10                                                    |
| Fixed in          | v4.1.11                                                              |
| Weakness          | CWE-200 (Exposure of Sensitive Information to an Unauthorized Actor) |

A `$NAME` reference in a monitor or trigger read any environment variable of the Kener process. A caller with write access could point a monitor at their own server with the header `X-Token: $KENER_SECRET_KEY`, and the next check sent the real value. With `KENER_SECRET_KEY`, a caller can sign a session for any user, admins included. The same worked for `$DATABASE_URL`, `$SMTP_PASS`, cloud credentials, and every other variable. Any API key and the built-in **Editor** role could do this.

Kener now reads only environment variables whose names start with `KENER_VAR_`. A reference `$NAME` reads `KENER_VAR_NAME`. Any other reference stays as literal text. See [Custom variables](/docs/v4/setup/environment-variables#custom-variables).

> [!WARNING]
> **Breaking change.** Rename each environment variable that a monitor or trigger references: `API_TOKEN` becomes `KENER_VAR_API_TOKEN`. You do not need to edit any monitor or trigger, because `$API_TOKEN` keeps its name. Until you rename a variable, Kener sends the literal text `$API_TOKEN` and logs a warning that names the new variable.

What to do:

1. Before you upgrade, rename the referenced variables in your `.env` file, compose file, or deployment settings.
2. If anyone held an API key or a `.write` permission for monitors or triggers, and you did not trust them, treat every environment variable of the Kener process as exposed.
3. Rotate `KENER_SECRET_KEY`. This signs out every user and disables every API key, so create new keys afterward.
4. Rotate the other secrets in that environment: the database password, the SMTP password or Resend API key, and any cloud credentials.
