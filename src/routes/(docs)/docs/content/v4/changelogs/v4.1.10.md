Release date: **October 26, 2026**

> [!IMPORTANT]
> This release fixes a security issue in v3.0.0 to v4.1.9. If `KENER_SECRET_KEY` is unset, empty, or an example value from the docs, set a new random value. See [Security](#security).

## Security {#security}

### Sessions could be forged when `KENER_SECRET_KEY` was unset or empty {#fallback-secret}

| Field             | Value                                                                                                     |
| ----------------- | --------------------------------------------------------------------------------------------------------- |
| Affected versions | v3.0.0 to v4.1.9                                                                                          |
| Fixed in          | v4.1.10                                                                                                   |
| Severity          | High, CVSS 3.1 score 8.1 (`CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:H/I:H/A:H`)                                 |
| Weakness          | CWE-798 (Use of Hard-coded Credentials), CWE-1188 (Initialization of a Resource with an Insecure Default) |

When `KENER_SECRET_KEY` was unset or empty, Kener signed and checked every session token, password reset link, and invitation link with the fixed string `DUMMY_SECRET`. Kener also hashed API keys with it. Anyone who knew that string could forge an admin session or a password reset link for the instance. Kener gave no warning.

Kener now has no fallback key:

- An unset or empty `KENER_SECRET_KEY` turns off sign-in, password reset, and API keys. The sign-in page shows **Set up not completed**.
- Kener logs a startup warning when the key is unset or is an example value from the docs, such as `replace_me_with_a_random_string` or `some_secret_key_for_kener`. These values are public too, so anyone can forge sessions for an instance that uses one.

What to do:

1. Check `KENER_SECRET_KEY` on your instance. If it is unset, empty, or copied from the docs, `docker-compose.yml`, or `.env-min.example`, set a new value: `openssl rand -base64 32`.
2. Upgrade to v4.1.10 and restart.
3. Sign in again. Changing the key signs everyone out.
4. Create new API keys under **Manage → API Keys** and delete the old ones. Changing the key stops every existing API key.

## Documentation {#documentation}

- [Authentication](/docs/v4/api-reference/authentication) no longer describes per-key permissions, key expiry, `KEY_EXPIRED`, rate limits, or `/api/me`. Kener has none of these. Every API key has full access to `/api/v4`.
- [Environment Variables](/docs/v4/setup/environment-variables#kener-secret-key) now says what happens when `KENER_SECRET_KEY` is missing, and that changing it stops every existing API key.
- [User Management](/docs/v4/user-management#permission-domains) now warns that `monitors.write` gives server access.
